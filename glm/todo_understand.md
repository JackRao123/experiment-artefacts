Both deep-reads are done (one on the trainers diff, one on the submodule chain — Bridge #12/#16/#17, Megatron-LM #7/#13/#14/#15). Here's the synthesis.

The single highest priority

The pre-shifted-label invariant, and why it makes the CP loss path correct at rank boundaries. This is the crux of the whole PR: pack_thd_cp_microbatch shifts labels per document (labels = tokens[1:] + [-100], packing.py:854) before zigzag sharding, so every local position already carries its own target — including the rank-boundary position whose target token physically lives on another rank. That's what lets chunked_lm_head.py score all S_local positions with targets_pre_shifted=True instead of the default drop-the-last-position convention (hidden[:-1] vs labels[:-1]). The invariant to be able to state cold: after packing, every position's label is either its true next token or −100 (doc end, pad, global end), independent of how the row is later partitioned. This is also the merge resolution the PR body explicitly asks Jerry to review, and it's where a mistake trains silently wrong rather than crashing.

2. The gradient-scaling cancellation. A reviewer will ask "why don't you divide by cp?" The chain (all verified in the pinned sources): Megatron's schedule multiplies each CP rank's backward seed by cp (schedules.py:340), mcore DDP pre-scales grads by 1/(dp·cp) (distributed_data_parallel.py:203), so cp cancels exactly and the controller applies only 1/loss_tokens at megatron_controller.py:2563 — the comment block there records that an earlier iteration had a wrong extra 1/cp. Empirical anchor: cp1-vs-cp2 grad-L2 832.3 vs 845.8.

Loss/token reduction over dp×cp + the PP broadcast. _loss_report (megatron_controller.py:592) all-reduces [loss_sum, num_active] over the dp×cp group — sum, not average, because CP ranks hold disjoint token sets — and non-last PP stages only get loss_tokens via the broadcast at :2475-2493; without it their gradient scaling is silently skipped. Wrong group membership here mis-scales every gradient.
